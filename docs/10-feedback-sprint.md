# Feedback Sprint — Teacher UX Review

This is deliberately named the **Feedback Sprint**, not "Sprint 7" — it isn't part of
the six-slice build plan in `decisions.md`. It's a response to direct teacher
feedback on the live app after Slices 1–6, tracked separately so it's obvious to
anyone marking this project which work was originally planned and which was a
reaction to real review.

Due date was extended to next Friday when this feedback was given, which is why
this sprint takes the time to design and agree a plan before writing any code,
rather than patching the UI directly.

## Teacher feedback (21/8/26)

Given verbally, relayed to Claude and discussed together:

1. The current card-grid-and-filters layout won't hold up once a user has a
   realistic number of items — at around 100 items it will look cluttered.
2. Suggested seeding the database with a realistic volume of items first, to
   actually see what the system looks like under real load rather than guessing.
3. The landing page should be a **dashboard**, not a raw list of every item — a
   summary that's quick to read.
4. The dashboard should surface warnings and items close to expiring.
5. The dashboard is the home screen; from there, intuitive navigation (buttons,
   etc.) takes the user to specific places — e.g. "the fridge," or "what's
   expiring soon" — rather than everything living on one flat page.
6. Add the ability to switch between a **card view** (the current design) and a
   **list view** showing items with their stats.

The teacher also shared three screenshots of generic admin-dashboard templates
(stat tiles, donut/bar charts, a sidebar) as reference material for the *kind* of
structure being asked for — not a literal design to copy.

## Discussion & decisions (21/8/26)

**Sequencing.** Wireframe first, built with a realistic ~100-item mock dataset
baked directly into the mockup, so the "does this actually scale" question gets
answered by the wireframe itself rather than being gated on a seeded database.
Once the wireframe's structure is agreed, seed the live database, then build the
real, styled UI against that structure, then verify it against the real seeded
data.

**Wireframe format.** A real, self-contained, clickable HTML/CSS/JS mockup — not a
static image — so the navigation flow and the card/list toggle can actually be
clicked through rather than just looked at. First pass is deliberately
low-fidelity (grayscale, boxes-and-labels) so the discussion stays on structure,
not visual polish, until the structure itself is agreed.

**Dashboard content.**
- Stat tiles: total items, expiring soon, expired, unsafe.
- A "needs attention" list — the actual soonest-expiring items by name, not just
  a count.
- Quick-nav tiles: Fridge / Freezer / Pantry, each jumping straight to that
  storage location's filtered view.
- A donut chart of status breakdown (Fresh / Expiring soon / Expired / Unsafe) —
  answers "how many of each status" visually, using the app's existing status
  colours.
- A second donut chart of items by storage location (Fridge / Freezer / Pantry).
  Deliberately *not* doing a by-category donut on the dashboard — 11 categories
  is too many slices for a donut to stay legible; a table or bar chart would be
  the honest form for that if it's wanted later.

**Navigation structure.** Claude proposes a first structure (dashboard as home;
Fridge / Freezer / Pantry / Expiring Soon / All Items as destinations reachable
from it), for the user to react to and reshape rather than getting it handed
down as final.

**List view.** Show every stat per item in the first pass; if that's too crowded
at real density, trim columns based on what the wireframe actually looks like at
~100 items, rather than guessing which columns to cut up front.

**Search / filter / sort.** Must behave identically in both card view and list
view — same toolbar, same result set, just a different presentation of it.

**Visual style.** A blend, not a rebrand: the app's existing colours, typography,
and icons stay, but the layout gets denser and more dashboard-like in the way the
reference screenshots were (stat tiles, charts, quick-nav), rather than adopting
those screenshots' own colour scheme or sidebar chrome wholesale.

**Seeding.** Roughly 100–150 items, seeded against the user's own real account
(so it shows up in actual use, not a separate throwaway account), with a
deliberate spread across every status, every storage location, and every
category — not accidentally skewed to all-fresh or one category, since the
whole point is stress-testing the "does this scale" question honestly.

## Wireframe

The rough, clickable HTML wireframe lives at
[`docs/wireframes/feedback-sprint-dashboard-wireframe.html`](wireframes/feedback-sprint-dashboard-wireframe.html).
It's a self-contained file (mock data generated by a seeded RNG so the same
~112-item dataset appears every time it's opened) — download it and open it
directly in a browser to click through it; it isn't wired to Supabase or the
real app.

**First pass (21/8/26):** dashboard with stat tiles, needs-attention list,
status/storage donuts, and Fridge/Freezer/Pantry/All-items quick-nav; a list
page with the card/list toggle and the same search/filter/sort as the real app.

**Second pass, after review (21/8/26):** the first pass was agreed as a good
starting structure, with four refinements requested:
- Items are now sorted by default everywhere (both card and list view) by how
  close they are to expiring — unsafe items pinned first as a food-safety
  alert rather than a countdown, then ascending by days.
- Clicking Fridge / Freezer / Pantry from the dashboard no longer jumps
  straight to that place's full item list. It now opens a smaller, scoped
  "place dashboard" first (stat tiles + a needs-attention list, scoped to that
  place) — the same "don't show more than needed by default" idea as the main
  dashboard, applied one level down. The full list is still one click away via
  a "View all `<place>` items" button.
- On phone-width screens, the list view's table now shows only Name, Days
  left, and Status by default — the other columns (category, storage, expiry
  date, quantity, opened) are hidden. Tapping a row expands an inline detail
  panel showing the rest. Desktop is unaffected — it keeps showing every
  column, and rows aren't clickable there since there's nothing hidden to
  reveal.
- The breadcrumb now supports a third level for this new place-dashboard step,
  e.g. `Dashboard › Fridge › All Fridge items`.

Both passes were verified with a disposable Playwright screenshot harness
(desktop 1440×900 and phone 375×812, checking the default sort order, the new
place-dashboard, the breadcrumb text, and the mobile row-expand interaction)
before being treated as done — same verification standard as the real app's
recent bug fixes.

## Database seed

With the wireframe agreed, the next plan-of-attack step is seeding the live
database with a realistic volume of real data. The seed script lives at
[`supabase/seed/feedback-sprint-seed.sql`](../supabase/seed/feedback-sprint-seed.sql) —
135 items, seeded against the user's own real account, spread across every one
of the 11 categories, all 3 storage locations, and all 4 statuses (fresh /
expiring soon / expired / unsafe), deliberately not skewed to all-fresh.

Rather than picking random dates and hoping they land in a sensible spread,
each row's printed expiry date (or date opened, or date prepared for
Leftovers) was computed by *inverting* the real Adjusted Expiry Date Algorithm
(`decisions.md`) for a chosen target — e.g. "I want this item's ADJUSTED
status to be 'expiring soon'" — then every row was checked *forward* through
the same algorithm before being written to the SQL file, to confirm it
actually lands in the intended bucket rather than just looking plausible. See
`decisions.md`, "Feedback Sprint database seed" for the full approach and the
real bugs this two-way check caught before the file was finalised.

**Run.** Confirmed run by hand in the Supabase SQL Editor against the live
project. The script's commented-out `delete from items where user_id = ...`
cleanup line was left as-is (not needed/used) — the seed landed on top of
whatever was already in the account.

**Account mismatch found and fixed.** After the real UI was built, none of
the seeded items actually showed up in the app. Turned out both this seed
and the original Slice 1 `seed.sql` had been written against a different
account of the user's than the one signed into the app — the insert
succeeded, but Row Level Security correctly hid every row from the account
being used to check it. Fixed with a single `update` re-parenting all 155
previously-inserted rows onto the correct account (rather than re-running
either seed and duplicating the data), and corrected the hardcoded UUID in
both seed files. See `decisions.md`, "Feedback Sprint seed account
mismatch," for the full diagnosis and fix.

## Real UI build

With the seed run, `App.tsx`/`ItemList.tsx` were rewritten and two new
components (`Dashboard`, `PlaceDashboard`) added, matching the wireframe's
agreed structure: a Dashboard landing page, a scoped PlaceDashboard per
storage location, and the full item list (now with a card/table view toggle
and a single flat urgency sort, no more grouped sections) reached
deliberately from either. Full reasoning for every decision made while
building this — dropping the old grouped-sections UI, reusing the existing
item modal for table rows instead of a new inline expand-row, the new
"Needs attention" filter, dropping the table header's stickiness, and the
validated storage-location colour palette — is in `decisions.md`, "Feedback
Sprint: real UI build."

Built and verified in a disposable sandbox with its own `npm ci`: `tsc -b
--force`, `eslint .`, and `npm run build` all pass clean. Beyond that, a
disposable Playwright harness rendered the real components against a
~120-item generated dataset and screenshotted the whole flow — dashboard
(light + dark), place-dashboards, both list views, every breadcrumb depth,
and the full mobile flow (including tapping a table row to confirm it opens
the existing modal) — with zero console/page errors. One real bug was
caught and fixed this way: a status pill's `white-space: nowrap` fought the
mobile table's column width and pushed "Expiring soon" off the edge instead
of wrapping.

**Not yet done:** confirming the real, Supabase-connected app renders
correctly against the actual live 135-item seeded dataset — the Playwright
pass above used a generated mock dataset in an isolated harness, not the
real account's data, since this sandboxed session has no Supabase
credentials to check that directly.

## Plan of attack

1. Build a rough, low-fidelity, clickable HTML wireframe (mock data, ~100 items)
   covering the dashboard and every destination page, plus the card/list toggle.
2. Review it together and iterate until the structure is agreed.
3. Seed the live Supabase database with a realistic volume of real data.
4. Build the real, styled UI against the agreed structure.
5. Integrate it against the live, seeded data and verify it actually holds up at
   that volume — not just in the mockup.
